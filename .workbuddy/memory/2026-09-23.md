## 一、AI 面板布局重构（frontend/src/components/AiAssistant.tsx + styles.css）

### 真相：挤压逻辑「代码里有，但用户看不到」
排查发现旧实现已经是**两个正交布尔量**：`docked: boolean` + `layoutMode: 'desktop'|'mobile'`。
CSS 里 `.ai-cockpit-panel.workstation-sidecar` + `html.workstation-docked .app-shell`
在 ≥1100px 时确实会挤压（1680 → 1260）。所以「没有这个功能」的真实原因是：

- 入口是一个**无文字的 `PanelRight` 图标按钮**，和旁边的手机/显示器图标长得一样，无从发现；
- `docked` 默认 `true`，新用户一打开就已经在停靠态，反而以为那两种图标才是「布局切换」；
- **停靠时「桌面/手机」切换是空操作**（sidecar CSS 强制单列），用户点了没反应；
- **<1100px 时 `docked=true` 静默失效**：媒体查询不匹配，既不挤压也不降级，面板还按
  `min-width: min(980px, ...)` 铺在内容上（1024 视口下 shell 宽 1080 直接横向溢出）；
- **两份并行实现，其中一份是死代码**：`ai-cockpit-sidecar-active`（3 处）与
  `.ai-cockpit-panel.sidecar`（6 处）+ `.ai-cockpit-sidecar-toggle` 从来没有被任何 TS/TSX 应用过。

### 改法：单一三态模型
```ts
type AssistantLayoutMode = 'floating' | 'docked' | 'phone';
```
- `floating` = 原 `desktop`（大浮窗，可拖可缩放，不占日志区宽度）
- `docked`   = 紧靠右侧 + 挤压 `.app-shell`（用户要的那个）
- `phone`    = 原 `mobile`
- `docked` 由 `layoutMode` **派生**，不再是独立 state；旧 key 一次性迁移
  （`layoutMode-v2` + `tracelens-workstation-docked` → `layoutMode-v3`）。
- 头部换成**三段式显式切换控件**（`.ai-cockpit-layout-switch`：悬浮/停靠/手机，
  `aria-pressed` + 高亮），悬停有中文说明——可发现性问题从根上解决。
- 宽度与挤压量共用 CSS 变量 `--ai-dock-width` / `--ai-dock-gap`，两处不可能再漂移。

### 窄屏不再静默失败
`@media (max-width: 1099px)`：不挤压，面板变成右侧覆盖抽屉（`.dock-overlay`），
并在面板顶部显示 `.ai-dock-notice` 说明 + 一键「切浮动」。
另外修了 `clampLayout`/`clampMobileLayout` 的老 bug：只为拖拽留了「挂出屏幕边缘」的余量，
但 resize 时也沿用了它，导致 1680px 上摆好的面板在 1000px 窗口里**整个右侧跑出屏幕**
（`gapRight` 为负）。新增 `fitLayoutToViewport()` 只在 resize 时收拢，不破坏拖拽语义。

### 清理
删除 7 段死 CSS（`ai-cockpit-sidecar-active` ×3、`.ai-cockpit-panel.sidecar` ×4 组、
`.ai-cockpit-sidecar-toggle`），旧 `layout-desktop/layout-mobile` 全部重命名为
`layout-floating/layout-phone`。
验证：1680/1280/1100/1000 四档 × 三模式，`gapRight` 全部 ≥ 6；≥1100 停靠时 shell 精确减 420。

### 重启后验证时发现：语义路由的 LLM 调用 100% 返回 HTTP 400
```
{"error":{"message":"Thinking mode does not support this tool_choice", ...}}
```
DeepSeek 的 `deepseek-flash` **默认跑在 thinking 模式**，而 thinking 模式**不支持**
`tool_choice: "required"` 和强制 function 的 `tool_choice`。而 TracePilot 的
`SemanticRouter` 恰恰用强制 `tool_choice={"type":"function","name":"select_tracepilot_route"}`
来让 AI 决定「这轮该用哪些工具」——也就是用户最核心的「AI 决策」链路。

后果不是报错，而是**静默劣化 + 巨大延迟**：每次路由都吃满 7 次重试的指数退避
（base 3s / max 90s，`TRACELENS_AI_RETRY_*`），然后回退成不过滤的全量工具集。

实测探针：
| 请求形态 | 结果 |
| --- | --- |
| `tool_choice: "auto"` | OK |
| `tool_choice: "required"` | 400 |
| 强制 function | 400 |
| 强制 function + `thinking:{type:disabled}` | **OK** |
| 强制 function + `reasoning_effort: low` | 400 |
| `deepseek-v4-pro` 强制 function | 400 |

### 修复（`backend/apps/tooling/llm/client.py`）
沿用文件里已有的 `stream_options` 兼容重试套路，新增 `_degrade_tool_choice()`：
1. 首次遇到「tool_choice 相关 400」→ 关闭 thinking（**保住强制路由**，信号最强），立刻重试；
2. 若仍被拒 → 降级为 `tool_choice="auto"`，再重试；
3. 学到的能力标记缓存在 client 实例上（`_thinking_disabled` /
   `_forced_tool_choice_unsupported`），**后续调用不再付那次失败的往返**；
4. 三条调用路径全部接入：`chat` / `achat` / `stream_chat`。

**坑**：`thinking` 不能直接作为 kwarg 传给 `chat.completions.create()`——OpenAI Python SDK
会在客户端就校验参数名并抛 `unexpected keyword argument`。必须走 `extra_body`：
`kwargs["extra_body"]["thinking"] = {"type": "disabled"}`（`_set_thinking_disabled()`）。

新增回归测试 `backend/tests/test_llm_tool_choice_compat.py`（5 例，用
`object.__new__(LLMClient)` 绕开 Django settings 和网络，纯逻辑测试）。
`backend/.venv` 原本没装 pytest，用 `uv pip install --python .venv/bin/python pytest` 补上。

验证：端到端 `POST /api/tools/assistant-chat-stream/` 用「现在几点」触发真实工具调用，
3.1s 返回正确时间，网关 400 归零，`tool_choice_compat` 警告只出现一次。

### ★ 关键发现：插话能力后端早就写好了，只是 UI 从没接上

### 实现
- 队列行：序号圆徽 + 文本 + `✏️取回编辑 / 🗑删除 / ↑插话`；移除了原来那个**假的拖拽手柄**
  （`GripVertical` 纯装饰，没有任何排序实现）。

### ★★ 顺带修掉的「谎报」问题
后端 `guide()` 返回 True 只代表**已进入本轮引导队列**，不代表会被采纳——
如果 run 刚好走完最后一个 plan，`finish()` 会 `_guidance.pop()` 把它丢掉，而前端已经把它

- `phase=guidance` 事件 → `applied`（「✓ 本轮已采纳」）
- `done` 事件仍 pending → `missed`（「本轮已结束，未采纳」橙色）

## 七、跨会话排队 bug + 架构重构（第三批）

### 1. 排队 drain 的两个 bug（`AiAssistant.tsx`）
- **全局 FIFO**：`taskQueue[0]` 是所有会话共用的队列头 → A 会话的积压会把 B 会话的消息压到后面。

## 八、实况日志修复 + 补充 9 个 tool（第四批）

### ★ 实况日志为什么一直是空的（用户报的 bug）
`apps/logsources/views.py::live` 把**同步生成器**交给 `StreamingHttpResponse`。Django 只支持
异步迭代，遇到同步迭代器会走：

```python
for part in await sync_to_async(list)(self.streaming_content):   # django/http/response.py:546
    yield part
```

`list()` 对**永不结束**的 live 生成器永远不返回 → **浏览器一个字节都收不到**，
连接就那么挂着。远端打印得再欢也没用。

**这正是 2026-09-21 修过、后来丢失的修复**（当时改成异步生成器，现在代码又变回同步了）。

修法：新增 `backend/apps/common/streaming.py::iter_sync_stream_in_thread()`
—— 把阻塞生产者的线程与事件循环之间用有界 `asyncio.Queue` 桥接：
- 有界队列 = 天然背压，慢客户端不会把内存吃爆
- 消费者取消（浏览器断开）→ `stopped` + 排空队列让生产者**及时退出**，
  由生产线程自己 `close()` 源生成器（避免跨线程 close 的竞态）
- 生产异常转发给消费者
`live` 和两条 `stream` 响应（命中缓存 / 未命中）都接上了。
顺带把有限的 `stream` 也修了：以前**整份结果先物化在内存里**，前端要等搜完才看到数据。

### 设计要点（我给的更优方案，逐条已落地）
1. **不新建"监控规则"概念** —— 给现有 `DisplayRule` 加引用即可。
   `LogWatch.source_rule_id` **只存 id，不复制规则体**，规则设置页仍是唯一真相。
2. **服务端常驻 + 共享 tail** —— 新增 `TargetHub`：**每个 (环境, 目标, 日志类型) 一条 SSH tail**，
   N 个 watch / N 个浏览器共享。现在浏览器关掉监控照样跑。
   （原来的实况日志是"每个标签页一条 tail"，且关页面就断。）
3. **触发不止"出现"** —— `appear` / `burst(窗口内 N 次)` / `silence(静默)` 三种。

4. **LLM 用在触发上，不用在流上** —— 逐行送模型又贵又慢又不确定；
   匹配是确定性 Python，模型只负责写规则和解释命中。
5. **seq 续传而非时间戳** —— 每个 watch 用 Redis `INCR` 分配单调 `seq`，

7. **规则健康可查** —— `GET /api/log-watches/rule-health/` 返回编译成功数 + 失败原因。

### ★★ 顺带挖出并修掉一个严重 bug（HTTP 400）
跑端到端时任务**直接失败**：
```
An assistant message with 'tool_calls' must be followed by tool messages
responding to each 'tool_call_id'. (insufficient tool messages following tool_calls message)
```
把发给网关的消息 dump 出来，顺序是：

**修法**：把这类 system 说明收集到 `deferred_system_notes`，
**等所有 tool 回复都就位后**再统一 append。
另外补了一条不变量兜底：回合结束时若有 `tool_call` 没被回复，补一条占位 tool 消息，
避免"某个分支跳过回复"再次炸掉整轮。

这是一个**能编译、能跑、之前测试全绿**的潜伏缺陷 —— 只在模型一次发多个工具调用

## 二十、实时监听不再清空当前 tab，改为另起一个 tab

### 根因
开启实时监听时有一段 `sameActiveTarget` 分支：**当监听目标与当前 tab 的目标一致**时，
它会**复用当前 task 并把 entries / issues / 时间范围全部清空**：

```ts
if (sameActiveTarget && activeTask) {
  setTasks(... entries: [], issues: [], loadedStartNs: undefined, ...)
}
```

所以"查了 cpfr/cpfr 的日志 → 对同一个模块点实时监听"会**直接毁掉你正在看的那个 tab**。

### 修法
**实时监听永远新建独立 tab**（`实时 · <环境> · <模块>`）：
- 删掉整个 `sameActiveTarget` 复用/清空分支（该变量也一并移除）
- 建 task 改为无条件执行
- 理由不止是"别清空"：**流式 task（无时间范围）本来就不该和快照 task 挤在同一个 tab 里**

静止检查：`sameActiveTarget` 已完全移除；剩余的 `entries: []` 只出现在
新建 task / 解析器内部，没有别处会清已有 task。

### ⚠️ 验证程度
**只做了静态检查，没能在浏览器里跑通。**
`实时监听` 开关的启用条件是
`!rawLogMode && remoteLogLocator?.environment && remoteLogLocator.liveTargets.length === 1`，
而 `liveTargets` 来自用户在查询面板里的**显式勾选**，共享场景 URL 不会填这个字段 ——
所以我用 URL 驱动的自动化跑不到"点开实时监听"那一步。

后端 239 passed；前端 tsc 干净 + 3 组自检通过。

## 二十一、会话上下文：改为「每轮实时采集」，不再冻结在会话建立时

### 用户诉求
> 会话上下文应该自动加上当前页面的上下文

## 二十四、日志搜索支持多关键字（任一命中）

**「任一关键字命中任一字段」**（OR）。

**语义选择**：用户说的是"多行符合**不同**关键字"，所以是 **OR 而不是 AND** ——
AND 只会让结果更少，与诉求相反。

输入框占位符与 title 也写明用法。

**注意**：`query_skills.py:239` 早就有同类实现
（`any(keyword.casefold() in line.casefold() for keyword in keywords)`），

## 3. 仿真 shell 的 find 静默返回空（连带 CPD 报告列表 0 份）
排查「数据」按钮不存在时发现：CPD 报告页 `全部报告 0 / 当前范围 0`。
`_scan_catalog_parallel` 用 `find <root> -mindepth 1 -maxdepth 1 -type d -printf '%f\n'` 取子系统，
而仿真 shell 对**所有** find 都返回空 stdout + 退出码 0（连 `find /data/tracepilot -maxdepth 1` 也是）。

根因在 `simremote/shell.py` 的 `_FindSpec.matches_name`：
```python
if not self.groups: return True
for group in self.groups:
    if not group: continue      # ← 空组 = 没有 -name 约束
return False                    # ← 于是「不带 -name」判定为「一个都不匹配」
```
`groups` 默认是 `[[]]`，所以只要不加 `-name`，find 永远输出空 —— 而且退出码 0，
调用方看不出任何异常。改成空组 `return True` 后：
`find … -mindepth 1 -maxdepth 1 -type d -printf '%f\n'` → `spwsp/cpfr/mecore/sil`；
`-name "*.xlsx"` 仍然正常。重启 fleet 后 CPD 数据集 **0 → 24 份报告**，
「数据」按钮也从 0 个变成 24 个。
**教训**：仿真层用「退出码 0 + 空输出」表达失败，比报错更难查；改仿真命令时要按真实 find 语义
（无过滤器 = 全匹配）写，并且改完用「空过滤器」用例自测一遍。

## 7. AI 结论 → 案例：一次回答就够，而且真的存得进去
用户报的两件事其实是一条断掉的链路：
「ai分析出根因后还要再跟ai交互一次整理结构化」+ 保存案例报
`POST /api/abnormal-cases/` 400 `{evidences:["第 1 条举证缺少原始日志或指纹模板。"]}`。

### 根因一：AI 整理的举证**永远**存不进去（就是那个 400）
`draft_diagnosis_case` 产出的举证是
`{"raw": ..., "component": "", "timestamp": "", "source": "tracepilot"}` —— 没有 `template`。
而 `_normalize_evidences` 要求 `raw` **和** `template` 都在，于是「整理成案例 → 保存」
这条路径 100% 返回 400。实测复现后再修，确认是同一个报错。
> 教训：产出举证的一方和校验举证的一方对「一条合法举证长什么样」理解不一致，
> 而且没有任何测试覆盖这条链路（只覆盖了静态字符串）。

### 根因二：校验假设「案例一定是日志报错」
同一份校验还要求案例里**至少有一条命中异常规则的运行日志证据**，报告证据只能作补充。
用户指出：有些用例场景的案例根本不是日志报错，而是**用例报告执行过程本身的报错**
（断言失败、超时、pytest/xytest 报错）—— 它们没有日志行、没有异常规则，却最该沉淀。
`atlog/knowledge_bridge.build_ai_case_evidences(require_runtime=True)` 里那句
「AI 报告缺少可回链的运行日志异常证据，不能保存为案例」是同一个错误假设的另一半。

### 做法
1. **新增 `apps/knowledge/evidence.py`：一条举证算不算有效、能不能指纹匹配，只在这里判定。**
   - 有效性：`raw` 或 `message` 有内容即可。`template` 缺失时**推导**（`normalize_template`），
     `tokens` 缺失时按模板推导。不是错误。
   - 举证类型（`evidence_kind`）：`runtime_log` / `case_report` / `case_fragment`。
     显式声明优先；否则按来源和字段特征保守推断（有异常规则或 level/source_file 才算运行日志，
     其余宁可当成自由文本，也不要把一段说明文字伪装成能参与指纹比对的日志）。
   - `matchable`：只有「运行日志 + 命中异常规则」才为真。**这是质量信号，不是保存门槛**。
     报告证据和用例片段照常入库、照常参与文本相似度检索。
   - 序列化器新增只读字段 `matchable_evidence_count`，界面用它区分「能被同款日志自动命中」
     与「只能靠文本/人工比对」，替代了被删掉的那句硬校验。
2. **`draft_diagnosis_case` 负责产出合法举证**（谁产出谁补指纹），并接受
   `evidence_entries` / `source_task_name` / `environment_id` / `environment_name` / `query_snapshot`。
3. **绑定到被分析的那份日志由运行时注入，不由模型复述。**
   `kernel/context.py` 新增 `_inject_case_binding`：从 `log_locator` 取任务名/环境/时间窗/查询条件，
   并把 `selected_entry` + `displayed_evidence_entries`（前端新增的结构化版本，含真实
   `anomaly_rules`）作为 `evidence_entries`。模型只决定「现在该沉淀了」，抄错一次案例就挂错日志上。
4. **一次回答就够**：`case_draft` 卡片载荷里带上完整的 `case_draft_result`；前端 `done` 事件里
   直接把它挂成 `message.caseDraft`。于是**本轮回答里就出现案例草稿卡片**，
   「整理成案例」按钮（它 `!message.caseDraft` 才渲染）自动消失 —— 不再有第二次模型调用。
5. **取消日志类型限制**：`atlog/knowledge_bridge` 不再丢弃「既无异常规则又非报告来源」的行，
   `require_runtime` 不再抛错（降级为 warning）；编辑器新增「用例片段举证」输入区，
   可以直接贴用例报告/断言原文入库。非日志举证不再套日志行版式（原来会显示成
   `— | 未知模块 | LOG` 这种假字段）。

### 实测
- 复现：修前同一份 payload 必 400；修后 **201**，模板被推导
  （`<N>-<N>-<N> <N>:<N>:<N> CPFR INFO [Stage_EXPOSURE] 光源功率异常`），tokens 4 个。
- 纯用例报告举证（无日志、无异常规则）→ **201**，`evidence_kind=case_report`。
- 真空白举证 / 完全无举证 → 仍然 **400**（只该拒这种）。
- 带异常规则的真实日志举证 → **201**，`matchable_evidence_count=1`
  （修了一次数两遍的 bug：`evidences` 是 `feature_groups` 的扁平视图，两边都数会重复）。
- 浏览器（真数据）：AI 草稿卡片在**同一轮**出现、「整理成案例」按钮数 **0** →
  「确认保存」→ 编辑器预填案例名与 1 条举证 → 保存 **201**。原报错路径端到端打通。
- 浏览器：用例片段举证可添加、可保存（201）；片段行只显示原文 + 「用例片段」徽标；
  真实日志举证行版式未变（时间/模块/级别/来源照旧）。
- 仿真跑通：48 项 kernel 注入后 `case_draft` 带 `source_task_name=日志定位 · SIM-EUV-01`、
  `environment=2`、完整 `query_snapshot`。

### 回归
后端 `21 failed / 279 passed`，与基线**失败集合逐条一致**（用 `comm` 对比过）。
其中两条 `test_atlog_ai_diagnosis_static` 断言的是旧实现字符串，已随设计更新到新契约
（旧断言「必须有运行日志异常证据」正是被删掉的那条规则）。
`npx tsc -b`、`node scripts/test-workstation.mjs`、`npm run build` 全通过。
`test_atlog_analysis_service` 的两条失败与本改动无关：它们真的对 `10.29.108.45` 发 HEAD
（只 patch 了 `read_url_log_window`，漏 patch `probe_url_log_time_range`），
stash 掉全部改动后同样失败。

## 8. 规则配置框的「AI 一键自动配置」按钮
需求：新增数据提取器 / 新增语义规则的输入框和各个配置框，都加一个单独的 AI 按钮，
一键检测、自动识别、自动配置好。

### 已有的 AI 能力为什么不够
`LogRulesSettingsPage` 里本来就有一个「自动识别语义」，但它的前提是
`canAutoRecognizeSemantic = sourceFile.endsWith('.py') && sourceTargets.length` ——
只有「从 Python 源码带过来的日志」才能用，而且只填 `displayTemplate` 一个字段。
用户要的是**从样例日志本身**识别出整份配置，不依赖源码。

### 做法
**后端 `apps/tooling/rule_autoconfig.py`（新）+ `POST /api/tools/rule-autoconfig/`**
- `autoconfigure_data_extractor`：样例 → 数据集名、说明、Match 短语、字段（key/名称/类型/
  单位/字典路径）、作用范围、输出形式。
- `autoconfigure_semantic_rule`：样例 → 规则名、关键字、正文、参数、语义说明、
  补充说明、自定义标签文本与颜色、scope、displayMode。
- **模型只提议，代码验证**：每个字段的 `sampleValue`、每个参数的 `sampleValue` 必须是
  样例原文里的连续子串，对不上就丢弃并写进 warnings。模型很擅长把参数名写得像模像样，
  但只有真的出现在原文里的值才提取得出来 —— 这条线就是「AI 识别」和「AI 编造」的分界。
- 单位换算额外收紧：只在样例里真的出现该单位、且左右数值等价时才保留
  （单位配错会让绘图整体差一个量级，比不配更危险）。
- `focus` 参数让每个按钮的承诺落到实处：`fields` / `units` / `scope` /
  `semantic` / `label`。配置框里的按钮只合并它负责的那部分，不动用户已经调好的设置。
  实测 `focus=scope` 时 fields 保持原样，不会被顺手替换。

**前端 `components/AiAutoconfigButton.tsx`（新，共用）**
- 按钮 + 结果回显（填了什么 / 哪些被丢弃 / 置信度）做成一个组件，各处复用。
  否则「AI 给的东西能不能信」只能靠用户猜。
- 挂载点：数据提取器抽屉标题栏、划选步骤、字段定义、作用范围、**每个字段的单位换算框**；
  语义规则抽屉标题栏、粘贴样例、语义说明、自定义标签。
- 样例为空时按钮禁用并说明原因，不让用户以为按钮坏了。
- 数据提取器那边配完**立刻跑一次测试提取**，把真实提取值显示出来 ——
  「一键检测」得让用户看见它真的提出了数值。

### 实测（Playwright + 真实模型）
- 提取器：一次点击 → 4 个字段（dose/focus/stage_temp/elapsed）+ Match「exposure done」+
  单位（us/um/C/ms），测试提取 `dose=3.4 mJ · focus=12.5 um · ...`，校验无错误。
- 单位框按钮：`原单位 us · 1 条换算规则`，换算行 `1000000 us = 1 s`。
- 作用范围按钮：子系统 `exposure`；fields 未被改动。
- 语义规则：`已填入语义说明 · 3 个参数 · 标签「初始化 {测量器名称}」`，
  校验「规则字段完整，可测试并保存」。

### 修掉两个自己引入的 bug（都是真跑出来的）
1. `{重试次数}` 被定位到 PID `1234` 里的那个 `3` 上，模板预览变成
   `[12{重试次数}4]`。原因是用 `indexOf` 找参数值，单个字符/纯数字会撞进别的数字里。
   改成：光标只前进不后退（AI 给的参数顺序就是出现顺序）+ 优先挑**不被字母数字包夹**的出现位置。
2. 标签 focus 时模型发明了 `{模块名}` 这个不存在的参数，界面提示
   「自定义标签中的 {模块名} 没有对应参数」，规则存不下去。
   改成：把已有参数名作为提示传给后端；后端清掉标签里不存在的占位符并写 warnings；
   并且「给了标签却声明只显示语义」这种自相矛盾组合会被纠正为 `both`
   （标签只有 displayMode 含 label 才会被渲染）。

### 回归
后端 `21 failed / 279 passed`，与基线失败集合逐条一致（`comm` 对比）。
`npx tsc -b`、`node scripts/test-workstation.mjs`、`npm run build` 全通过。
验证未写库：0 个案例、规则未被保存（只填草稿）。
