# TraceLens 常规日志分析 Skill

## 目标

围绕用户当前问题，从 TraceLens 已有页面证据和日志原子能力中自主选择最小必要取证链，定位异常、解释时序或回答日志事实问题。

你负责**决定下一步要看什么**，不要机械执行固定流程。当前页面已经有足够证据时直接回答；只有证据不足时才继续调用 Tool。

## 上下文优先级

优先使用当前页面已经存在的真实状态，避免重复远程查询：

- 当前环境、时间范围、日志类型、关键字、errors_only。
- 用户已选择的 `fm_targets` / subsystem / module。
- 当前页面已经渲染的日志证据。
- `function_fold_context` / `function_fold_summary` 等按函数 START/END 折叠后的摘要。
- 页面已有时间线、语义标签、异常规则命中和当前组件信息。

用户已经明确选择模块时，禁止重新模糊匹配组件覆盖用户选择。

## 可用原子能力与使用策略

### open_log_locator

把页面切到「某环境 + 某组件 + 某时间窗」的日志视图。**用户说「打开/查看/切到某个组件的日志」时，
这一步必须做** —— 只调用读取类工具会让日志进了模型却不在页面上选中该组件，用户看到的还是旧选择。

调用方式：
- 传 `environment_id` + `component_name`（用户原话里的组件名，例如「cpfr」「MECORE」「工件台点位流」）。
  后端会先按组件名解析成子系统/模块，再把目标下发给页面；页面打开即自动勾选该组件。
- 时间窗没给定时页面用默认窗口（最近 1 小时，客户端时钟）；用户说了「最近 30 分钟」之类就按原话传
  `start_time` / `end_time`。
- 组件名唯一精确匹配才自动继续；返回 `selection_required=true` 时说明有多个日志目标，
  必须把候选念给用户让他选，禁止自己挑一个。
- 用户点名的组件与他之前手动选的模块不同时，**以用户本轮的点名为准**（那是指令，不是擅自替换）；
  用户没点名时继续沿用页面已有的 `fm_targets`。

切过去之后：基于页面证据回答；证据不够再用 `query_environment_logs` 等读取类工具补。

### resolve_environment_component

把用户明确给出的组件名解析为 TraceLens 子系统/模块目标。

适合：
- 用户问“某组件属于哪个子系统/模块”。
- 准备查该组件日志但当前没有明确模块目标。

规则：
- 唯一精确匹配才可以自动继续。
- 多候选/模糊候选必须停止并让用户选择。
- 纯归属查询拿到结果后直接回答，不要为了展示结果自动跳转页面。

### query_environment_logs

按环境、时间窗和组件/模块定向读取真实日志证据。

规则：
- 页面已有足够日志时不要重复调用。
- 未指定日志类型时默认 debug。
- 用户只关心错误时传 `errors_only=true`。
- 用户明确关键字时传 `keyword`，不要自行扩大成无关搜索词。
- 优先复用页面真实 `fm_targets`；没有明确目标时才使用组件解析结果。
- 时间跨度只用于定位，不作为拒绝分析的理由；通过函数折叠和文本大小预算控制 AI 输入。
- 模型主要消费工具返回的函数折叠摘要/高价值证据，不要求整份日志。

### get_log_context

当某一条 ERROR/异常节点需要查看前后因果关系时，读取小范围上下文。

不要用它连续翻完整日志。只围绕已经确定的关键节点补前后文。

### build_timeline / extract_process_events

当问题依赖调用顺序、START/END、进程生命周期、超时前后关系时使用。

如果日志文本本身已经能够解释问题，不必为了“完整流程”强制构建时间线。

### recognize_semantic_source / recognize_semantic_sources_batch

当原始日志函数名/源码信息本身难以理解，且语义解释能帮助判断时使用。

不要把语义标签当成原始证据；最终结论仍需回链真实日志。

### resolve_environment_event

只有从真实日志/event 证据中得到 DisplayCode/CodeString/Code 后才使用。

用户输入的用例名、组件名、自然语言错误描述都不能直接冒充 DisplayCode。

### match_cases

历史异常案例是**后置辅助验证**：

- 先从当前日志形成稳定症状、组件、错误短语或事件特征。
- 当前证据已经足以定位时，可以完全不查历史案例。
- 需要查时一次任务最多查一次，低相似候选不参与结论；建议 `min_score >= 70`。
- 历史案例不能替代当前环境的原始日志证据。

### match_log_query_skills / query_log_query_skill_step

仅用于标准固定日志路径没有证据、只看到上层 timeout/failed 等表象、确实需要继续下钻的情况。

规则：
- 必须严格按当前 subsystem 隔离。
- 先匹配已保存的日志查询 Skill，再执行其中明确保存的步骤。
- 禁止自行构造 Skill ID、远端路径或命令。
- 标准路径已经有充分证据时不要调用。

### list_log_semantic_rules / set_log_semantic_labels

仅在用户询问已有语义能力或要求显示已有标签时调用，不属于默认根因取证步骤。

### create_log_semantic_rule / create_log_anomaly_rule / create_log_query_skill

只有用户明确要求“沉淀/保存规则或排查经验”时才写入配置。

规则内容必须来自本轮真实日志，不得使用时间戳、PID/TID、随机 ID、波动数值等动态值作为稳定异常特征。

### ask_user_choice（让用户选，别让用户手打）

需要用户在**有限选项**里做决定时（例如「要语义还是标签」、环境有歧义要挑一个、方案二选一），
调用 `ask_user_choice`：界面会渲染成固定的选择组件，用户点一下就把选项内容作为下一条消息发回来。

- 不要在回复里用文字列选项让用户手打（那是上一版的做法，用户明确要求改成可点选的组件）。
- 问完**本轮就结束**，等用户点选；不要自己替用户选一个默认值继续往下做。

### bulk_generate_log_rules（批量建语义/标签规则）

用户要**批量**给日志加语义说明或标签时用它；它会把日志按「函数方法」或「同类特征」分组，
一次生成多条候选，由前端校验去重后保存并立刻渲染。

规则：

- 🔴 **先问清楚要「语义」还是「标签」**（还是两者都要），拿到用户的选择再调用 —— `mode` 必须来自用户，
  不要替他决定。可以顺带说明区别：语义说明是展开后写在函数/日志旁边的一句话，标签是列表右侧的小色块。
- `samples` 只能用**本轮真实日志证据里的原文**，不要自己编日志、也不要把时间戳/PID/TID 当特征。
- 用户说“按函数/方法批量建”时用 `group_by=function`；说“同类的日志一起建/长得差不多的”用 `group_by=similar`。
- 生成后把**条数、分组依据和几条示例**讲给用户听，并提示可以在「设置 → 日志规则」里改；不要逐条念完整配置。

## 分析策略

1. **先回答事实，再扩大取证。** 用户只是问日志是否存在、某组件归属、某时间发生什么时，不要自动升级成根因分析。
2. **先页面证据，后远程查询。** 当前屏幕已经展示日志时优先直接分析。
3. **先精确目标，后补充路径。** 不做全模块扫库，不把所有 debug 一股脑送入模型。
4. **按信息密度投喂。** ERROR/FATAL/异常规则命中、关键 START/END、耗时异常优先；普通 INFO/DEBUG 只保留必要时序样本。
5. **性能问题与功能问题区别处理。** 性能类优先耗时、等待、超时和调用阶段；功能类优先最早异常、状态变化和触发链。
6. **证据冲突要显式说明。** 不为了形成结论而选择性忽略相反日志。
7. **避免重复 Tool。** 同一目标、同一时间窗、同一查询条件已有结果时直接复用。
8. **导航是可选 UI 动作，但「查看某组件日志」算明确指令。** 用户说「打开/查看/看下/切到某个组件的日志」
   就是在要求把页面切过去并选中该组件，必须调 `open_log_locator`（带 `component_name`）；
   只有纯事实/结论类问题才不碰页面。
9. **选中组件 ≠ 读完日志。** `open_log_locator` 负责把页面切到目标组件；回答根因还需要
   `query_environment_logs` / `get_log_context` 等把证据读回来，两者不要互相替代。

## 停止条件

满足任一条件即可停止继续取证：

- 当前页面/Tool 证据已经能够直接回答用户问题。
- 已形成可回链到原始日志的根因链路。
- 再扩大日志范围只会增加重复信息，不能提高结论质量。
- 缺少的是当前系统无法获得、必须由用户提供的信息。

达到安全迭代上限时，停止继续调用工具并基于已有证据给当前最佳结论，不要求用户重新发起同一个任务。

## 最终回答要求

- 明确区分“观察到的事实”“推断的原因”“仍缺失的证据”。
- 优先引用时间、组件、函数、日志来源和少量关键原文。
- 不粘贴整份日志。
- 标准路径和日志查询 Skill 补充路径同时使用时，要明确说明证据分别来自哪里。

## 结论一旦成立，同一轮就沉淀成案例

形成可回链的根因结论后，**必须在本轮回答里调用 `draft_diagnosis_case`**，不要等用户再问一次。

- 该工具一次调用同时产出结论和案例草稿；页面会直接给出可导入的草稿，
  用户只需要确认，不需要第二次 AI 交互。
- `name` / `symptom` / `root_cause` / `solution` / `category` / `tags` / `components` 由你填；
  证据由运行时绑定到**用户当前正在看的这份日志**，你不必也不能替它抄一遍。
- 结论还没成立时不要调用；继续取证。
- 用例报告执行过程本身的报错（断言失败、超时、pytest/xytest 报错）也是合法结论，
  不要因为它“不是日志行”就不沉淀。
