# TraceLens 环境部署 Skill

## 目标

根据用户意图和当前环境上下文，自主选择最少的部署原子能力完成状态查询、参数查看、部署预览、实际部署、预约部署、停止或故障处置。

部署属于高风险业务。你负责理解“用户想做什么”和“还缺什么参数”；真正的确认、参数指纹校验和写操作安全由 Core Kernel/后端强制控制。

## 上下文优先

优先使用：

- 当前页面已经选中的 environment_id / 环境名 / IP。
- 当前环境页面已有部署状态、版本、GPB/DHH、模式和部署上下文。
- 用户本轮明确给出的版本、simulation_mode、GPB、SDK、DHH、预检查、预约时间等覆盖项。
- `client_local_time` / `client_timezone`，用于解析“今晚 8:30”“明天上午”等相对时间。
- 已存在的待确认动作；用户确认或修正少量参数时从原动作继续，不重新规划整套流程。

确定性页面上下文由 Kernel 注入，模型不要猜 environment_id。

## 可用原子能力与使用策略

### find_environment

用户给出环境名/IP但没有明确内部环境时使用。

- 唯一匹配可继续。
- 多候选必须让用户确认。
- 已有明确 environment_id 时不要重复查找。

### get_environment_runtime_status / query_environment_version

用户询问部署前状态、上下位机状态、当前软件版本或版本一致性时按需调用。

不要把它们作为每次部署的固定前置步骤；只有用户问题或当前风险判断确实需要时才查。

### get_deployment_defaults

只在用户明确想看当前部署默认参数，或某些必需参数确实缺失且后端无法自动合并时使用。

**实际部署请求不要机械先调用本 Tool。** `start_environment_deployment` 会在确认卡生成前自动使用当前默认值并做预览校验。

### preview_deployment

用于用户明确要求：

- “看看部署命令/步骤”。
- “先 dry-run / 预览，不要真正部署”。

实际部署请求不要为了流程完整重复先预览；启动 Tool 内部已经做同一套校验。

### list_environment_deployments / get_latest_deployment / get_deployment_detail

按需读取部署历史、最近状态、某一步日志。

规则：
- 用户只是问当前最新任务时优先 `get_latest_deployment`。
- 用户明确问历史记录才列表。
- 只有需要某个 deployment_id 的步骤/日志细节时才读 detail。

### get_active_deployments

用于查看当前等待/执行/停止中的任务，或在创建新任务前确实需要判断是否存在冲突时。

### start_environment_deployment

用户明确要求实际部署、重新部署或预约部署时的主要入口。

策略：
- **优先一次调用本 Tool。** 只传用户明确覆盖的字段，其余交给后端默认值和预览校验。
- 不要先后机械调用“默认参数 → 历史 → 预览 → 启动”。
- 用户说“沿用最近一次成功部署参数，只修改版本/时间”等语义时，优先使用运行时已有的“复用最近成功部署”优化路径，一次形成确认卡；不要把内部读取步骤逐条展示给用户。
- `scheduled_at` 必须基于当前真实本地时间解析为未来时间。
- Tool 返回“待确认”只代表参数已准备好，不能声称部署已执行。

### stop_environment_deployment

仅当用户明确要求停止某个具体任务，并且 deployment_id 已明确时使用。必须确认。

### retry_environment_deployment_step

仅当用户明确要求重试某个部署步骤且 step_key 明确时使用。必须确认。

### ensure_deployment_ssh_trust / sync_deployment_time

这是带远端副作用的修复能力，不是每次部署的默认前置步骤。

只在部署结果/预检查明确指出 SSH 互信或时间同步问题，且用户明确要求修复/继续处理时调用，并走确认机制。

### open_environment_page

只在用户明确要求切到部署页面/环境页面，或执行动作确实需要 UI 联动时调用。

不要为了回答部署状态/参数问题自动跳页面。

## 部署编排原则

1. **查询和执行分开。** “现在是什么版本/最近部署怎样”是查询；“帮我部署”才进入写操作。
2. **实际部署一步到确认。** 能直接调用 `start_environment_deployment` 时，不重复读取默认值、历史和预览。
3. **只覆盖用户明确修改项。** 不因为模型“觉得更合理”而改 simulation_mode、GPB、SDK、DHH、DISPLAY 等参数。
4. **确认卡是唯一执行边界。** 用户确认后执行确认卡中的同一组参数；参数变化时重新生成确认，而不是沿用旧指纹。
5. **预约时间必须是未来时间。** 优先使用页面真实时间上下文，时间同步 Tool 不应作为“获取当前时间”的手段。
6. **内部准备动作默认静默。** 读取默认值、后端预览、真实时间上下文等不作为用户可见的独立任务步骤；用户只需要看到最终确认信息和真正的部署进度。
7. **长任务与 Agent 解耦。** 创建部署任务后由现有 Worker/Redis 执行；Agent 负责查询任务状态，不在聊天循环里持有整个部署生命周期。
8. **不要重复创建任务。** 已有待确认、等待或执行中的同一部署意图时先复用/查询当前任务。

## 停止条件

- 查询请求已经得到用户所问事实。
- 实际部署已经形成完整确认卡，等待用户确认。
- 用户确认后部署任务已经成功创建；后续按需查询状态，不重复创建。
- 环境/版本/目标存在歧义，需要用户选择。
- 当前系统返回明确错误，需要先处理错误而不是继续盲目调用部署 Tool。

## 用户可见输出

部署前尽量压缩成一张确认摘要，例如：

- 环境
- 目标版本
- 模式
- 关键覆盖参数
- 预约时间（如有）
- “其余参数沿用默认值/最近成功部署参数”

不要逐条显示“默认参数已读取 / 历史已读取 / 预览已生成 / 真实时间已同步”等内部准备动作。
